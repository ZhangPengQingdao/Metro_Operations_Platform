# 隐患提报 · 识隐 0.1.0

独立签名应用，使用公开 `@metro/platform-sdk`、共享 L2 组件和应用托管存储；不依赖旧 AFC 项目，不迁移旧数据。业务对照与权限说明见 [设计记录](../../docs/hazard-reporting-app-plan.md)。

## 工作流

1. 员工输入现场描述，可调用平台配置的模型获得隐患描述、分类、等级和治理措施建议。最多参考当前可读范围内的 4 条相似闭环案例；没有可用案例时不引用案例并要求人工复核。建议带置信度和复核标记，所有字段均可手工修改。模型不可用时仍可手工提报。
   提报弹窗提供 AI 提报和手动填报两栏；手动填报先选择线路，再选择本工班管辖的车站，治理责任人从本工班在岗人员目录选择。管辖车站由管理员在“基础数据 → 组织与工班”配置。
2. 提报后进入“整改中”；补充措施、时限、治理情况和整改后照片后提交安全复审。提报前照片可选。通过公开文件 SDK 在浏览器压缩为 JPEG，单张上限 220 KB，按块保存在应用私有托管存储；照片的读取需先通过隐患记录权限检查。
   照片上传使用独立的 `app.hazards.photo` 授权；提报人或治理人还须有目标组织的 `create` 或 `update` 业务授权。
3. 持有 `read`、`review` 权限且不是提报人的员工可查看证据并复审关闭。关闭与案例入库使用同一托管存储事务和版本条件。案例按完整度评分，70 分起参与后续建议；低分案例保留并标记待补充。`training_enabled` 始终为 `false`。案例库可按描述、分类和治理措施搜索。

## 授权与运行

- 员工需要应用使用授权和 `app.hazards.read` 才能打开页面，提报、治理、复审分别还需 `create`、`update`、`review` 权限。安全复审岗应获得所辖工班或部门的 `read` 与 `review`；仅授“本人”会被禁止自审。应用负责人或平台管理员身份不代替员工业务身份。
- 应用服务申请 `platform.app_data.read/write`、`platform.locations.read`、`platform.people.read`、`platform.ai.complete`。模型地址和密钥只保存在平台，应用使用独立的受限文本补全操作；安装时由管理员审批服务授权。
- 照片分块写入可能在记录保存前留下未关联的上传。当前无后台清理任务，容量运维需关注应用存储；任何未知写入结果均不自动重试。
- AI 建议会逐页检查全部有权读取且达到质量门槛的闭环案例，用文本二元组相似度选出最相关的 4 条，不按创建时间截断。存储页超过结果大小限制时会缩小页大小；检索失败会报错，不返回不完整的“最佳案例”。当前不是向量检索，案例量很大时仍可能触及 Gateway 耗时或调用限额，后续应接入平台索引检索能力。旧云文档同步和历史案例迁移未接入。

## 本地验证

在仓库根目录构建 SDK 后执行：

```sh
npm --prefix applications/hazards test
npm --prefix applications/hazards run build
npm --prefix server run app-cli -- validate ../applications/hazards/dist
```

`dist/` 是本地生成文件，不提交。构建与校验不等于已安装；安装需按平台签名包、审批、授予员工权限和启用流程完成。
