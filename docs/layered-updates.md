# 分层镜像与应用维护更新（0.8.0）

## 发行与下载

签名 `release.json` 格式 v2 增加 `registry`，固定三个镜像的 GHCR 仓库与 sha256 摘要。`images` 保存配置摘要，发行时与完整归档及仓库 manifest 交叉核验。运行时仍验证 Ed25519 签名、仓库范围、架构和精确 RepoDigest；不按可变版本标签启动。

正常更新只拉取本机缺少的镜像层。PostgreSQL 配置摘要不变时复用已有镜像；数据库镜像变化仍要求人工升级。前端展示当前镜像、缓存复用和镜像完成数，不把镜像数量伪装成下载字节百分比。Docker 中断下载后可复用已经验证的层，但安装任务不自动重放。

发行流水线使用 GHCR 和 GitHub Actions 构建缓存。私有镜像须在宿主 root 的 Docker 凭据配置中配置 `read:packages` 权限；公有镜像可匿名拉取。GitHub Release 读取令牌不自动当作镜像仓库凭据，不在命令参数、日志或签名清单中存储令牌。首次发布须核对包可见性及目标服务器的拉取权限。

完整 `images.tar` 仍作为签名离线备用资产。需要归档传输时在宿主 `config.json` 设置 `imageTransport: "archive"` 后重启更新器；默认是 `registry`。该选项使用完整归档验签与导入，不在镜像仓库失败时悄悄改变传输方式。

## 维护与恢复

1. 下载与校验阶段不停止应用。
2. 确认安装后，由宿主通过专用 Unix socket 请求 API 进入维护；控制接口不注册到公网 HTTP。发起人必须仍是有效的平台管理员。
3. API 关闭新业务入口和普通管理变更，等待应用工作日志清空。快照记录任务 ID、发起人、应用安装 ID、版本、修订、启用状态、实际运行状态和每次启停进度。
4. 快照落盘后，通过既有生命周期停用此前正常运行的应用。逐项执行前后写入状态；不直接修改注册表或清除未知业务写入。运行异常、超过 60 秒仍有工作或快照规模超过 1000 应用时明确阻断。
5. 全部暂停后，宿主再次运行只读预检，停止平台、备份、迁移、切换并检查平台健康。
6. 重新加载快照，校验应用安装 ID、版本与修订、当前发布者/版本审批，恢复此前正常运行的应用。原本停用的保持停用；异常应用不会被当成正常应用启动。全部恢复确认后解除维护。

API 状态文件位于 `/opt/metro-platform/maintenance/state.json`，只挂载给平台 API，不挂载给业务应用；控制 socket 位于同目录。目录属于平台 UID 1000、权限 0700，socket 0600。宿主把收到的快照保存在 `requests/<任务ID>-applications.json`，备份包括维护目录。

使用现有生命周期会产生停用和启用的审计及修订，最终恢复启用意图；不是直接暂停 Docker 进程。快照不保存凭据或业务数据，不代替数据库备份。

## 故障边界

- 尚未暂停但发现工作阻断：保持维护和快照，管理员可核对后显式 `recover --mode restart-current` 取消更新并恢复已确认暂停的应用。
- 启停回执丢失：快照停留在 `stopping` / `starting`，拒绝自动重放，需核对生命周期证据。
- 已进入迁移：不得回滚到旧数据库或旧代码，沿用 `resume-target` 与已验证备份的恢复边界。
- 部分应用恢复失败：平台保持维护，快照保留每项结果。平台进程再次丢失时，已恢复应用的运行状态不能仅靠快照推定，需现场核对。
- 任务恢复不绕过应用签名审批、未知写入、租约或存储迁移检查。

## 从旧版接入

宿主协议 v3 不识别新清单，须先以受信副本更新 root 所有的 `updater.py` 到 v4。旧 API 没有维护控制接口，首次升级仍使用原有“应用已停用”预检，不能假装能从旧版自动生成运行快照。完成首次过渡到 0.8.0 后，后续格式 v2 版本间更新才使用自动维护流程。

发布前应在隔离 Linux 环境验证：首次安装、旧格式升级、同数据库摘要的分层复用、实际应用暂停/恢复、未完成工作阻断、进程中断及恢复。生产服务器上不以自动重试代替这些验收。
