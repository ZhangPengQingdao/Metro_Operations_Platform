# Linux 一键安装与管理员在线更新实施方案

状态：设计与待办，尚未提供可执行安装器或在线更新功能。当前版本 0.1.0；本方案不代表生产部署已完成。

## 用户流程

首次安装：在专用 Linux 主机执行固定版本安装器 → 填写域名与管理员初始化信息 → 检查资源、端口和网络 → 下载并验证发行包 → 创建独立数据库、角色和密钥 → 执行平台迁移 → 启动服务并检查健康 → 返回登录地址。

后续更新：开发提交到 GitHub → CI 测试/构建通过 → 发布带版本、摘要和可验证来源的 Release → 管理端显示可用更新与兼容性说明 → 管理员下载、确认安装 → 备份、维护、迁移、切换、健康检查 → 展示结果与审计。下载不等于安装；更新不会因普通 main 提交自动执行。

## 建议首版支持范围

- 首先支持专用 Ubuntu 24.04 LTS、Linux amd64；arm64 待构建与真实主机验收后开放，不能只改安装器判断。
- Docker Compose 管理 PostgreSQL、API、前端反向代理；发行镜像固定 digest，服务器不现场 npm install 或编译。
- 平台代码、数据库、密钥、上传包与应用 runtime 分开存放；更新只切换代码发行版本。
- 宿主更新器使用 systemd 服务与本机受控 Unix socket。API 仅提交严格的版本任务，不能提交 shell、路径或任意下载 URL；不把 root/sudo 或通用 Docker socket 交给网页进程。
- 现有应用 Docker 执行器仍需独立收敛与隔离设计；平台更新器和应用宿主的权限不能混为一个通用命令执行服务。
- 管理站点与应用静态资源域分离并验收 HTTPS/Cookie 隔离后，再开放生产沙箱应用。现有回环 HTTP 验收不能替代这一步。

## 需要新增的模块

| 模块 | 主要工作 | 验收标准 |
| --- | --- | --- |
| 发行流水线 | Dockerfile、多阶段构建、固定依赖、版本 manifest、GitHub Release、镜像/离线包、摘要与来源证明 | 在干净 Linux 上只靠发行包运行，平台/API/SDK 版本一致 |
| 安装器 | OS/架构/磁盘/端口检查；Docker 依赖处理；固定版本下载与校验；可重复执行与断点恢复 | 重复运行不覆盖密码、不重置账号、不删除既有数据库；失败后可诊断恢复 |
| 数据库初始化 | 专用持久卷、SCRAM、独立 API/迁移/存储管理身份、仅内部网络可达、所需 ACL | 普通 API 不得成为超级用户；32 项现有迁移及后续迁移可记录、重复执行不重放 |
| 首次配置 | 随机密钥、0600 文件或 secrets、管理员安全交互创建、HTTPS 配置 | 密钥不出现在终端日志、命令参数、Git 或浏览器更新响应中 |
| 更新目录与校验 | 当前/最新版本、更新说明、架构、兼容版本、迁移策略、下载摘要、签名/证明 | 篡改、错误仓库、错误架构、降级、未发布版本全部拒绝 |
| 独立更新器 | 持久任务、互斥锁、下载暂存、备份、维护与排空、迁移、版本切换、健康检查 | API 重启后仍可查询任务；并发、断电、磁盘不足、迁移失败不重复升级 |
| 管理端 | 系统更新页：检查、下载、确认安装、进度、结果、审计 | 仅具备平台更新权限的管理员可执行，非 GET 检查同源与会话 |
| 备份恢复 | 数据库、角色/ACL、应用数据、配置与密钥、安装包绑定信息的协同备份；恢复演练 | 在新实例恢复后能登录、读应用数据、验证权限和安装状态 |

## 数据库与托管存储

现有开发 compose 使用 POSTGRES_USER 初始化数据库，不能直接作为生产 API 身份方案。安装器可在它新建的专用实例内创建角色、数据库与 ACL；遇到既有实例要先检查所有权并显式选择接入模式，不能调整其他系统的 PUBLIC 权限。

当前托管存储管理连接要求超级用户并位于 API 进程中。生产安装前需要把高权限工作移到受控代理，收窄接口和进程权限。不能为了安装顺畅给普通 API 超级用户，也不能默认把应用托管标为生产可用。

备份不能仅保存前端文件或执行一次 pg_dump 就称为全量恢复。应用 schema、角色/ACL、数据库配置、加密密钥、应用包和迁移证据必须可对应恢复。数据库备份应使用适合恢复验证的格式，并在暂停写入或确定一致性边界后生成。

## 更新失败与回滚规则

1. 任务持久记录：queued → downloading → verified → backing_up → maintenance → migrating → switching → health_check → completed；失败保留阶段、版本和证据。
2. 安装前验证空间、数据库连接、运行版本和备份可用性；暂停入口并排空实际工作。已有未知应用写入或外部运行结果不得通过平台更新清除。
3. 只执行发行包声明的迁移；记录原始/目标版本、包摘要、任务 ID 与审计。API 重启不能触发第二次执行。
4. 未迁移数据库且新版本未成功启用时，可回退代码。数据库已迁移时，只有声明并验证兼容才回退代码；否则保持维护状态，按恢复策略处理。
5. 不自动用旧备份覆盖已接收新业务写入的数据库；还原需明确恢复点与数据影响。PostgreSQL 主版本升级是单独流程，不跟随普通平台更新。
6. 未知结果保留并阻断；不能删除任务、迁移账本或租约记录来显示成功。

## 私有仓库下载

当前源码仓库为 private。首版可使用仅针对该仓库、只读 Contents/Packages 权限的机器凭据（按实际分发渠道验证需要的权限），由更新器保存在本机受限文件中，不能回传前端或写日志；组织部署可再引入 GitHub App 短期令牌。另一方案是建立独立公开发行仓库，但是否公开发行包需要用户决定。

不在脚本内嵌 PAT，不让服务器复用开发者的广泛仓库写权限。私有 Release 重定向和下载鉴权须按精确 host 规则实现，避免把令牌转发给任意地址。更新来源证明必须绑定仓库、tag、commit 与工件，不只比较同一下载来源提供的哈希。

## 实施顺序

1. 先完成 Linux 发行包 + 专用数据库/角色初始化 + 命令行安装与手动升级；用全新 Linux VM 做安装、重复安装、升级和恢复测试。
2. 再完成独立更新器与任务恢复，使用 CLI 验证所有失败阶段。
3. 最后接管理端更新页面和权限审计，保留现有 UI 设计；服务端更新能力通过验收后再开放按钮。
4. 同阶段补生产资源域、高权限存储代理和应用宿主部署验证，分别报告管理平台与应用托管的就绪状态。

开始写安装器前需要确定：服务器系统/架构、域名与 TLS 方式、是否能访问 GitHub/GHCR、私有发行下载方式、是否需要离线安装。默认可先按 Ubuntu 24.04 amd64 + 在线安装编写并在 VM 验证，正式目标机安装另行授权。
