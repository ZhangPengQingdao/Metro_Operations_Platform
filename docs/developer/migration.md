# 改造已有项目

## 先阅读和评估

先识别项目入口、技术栈、模块、路由、身份、权限、数据表、外部服务、任务、文件处理、部署和测试。围绕实际业务流程追踪前后端调用，不只读 README，也不机械加载依赖目录、构建产物或机密文件。

输出整合清单：原功能、当前实现、平台对应能力、是否真实开放、保留/替换建议、权限与数据影响、待确认项。公共目录优先匹配稳定人员/组织/车站/设备ID，不能按名称静默覆盖原数据。

## 方案确认点

确认应用边界和应保留的业务流程；原账号与平台员工如何映射；哪些公共能力替换、哪些保留；原后端和数据库如何处理；历史数据是否迁移；角色和数据范围如何对应；哪些 API 准备开放；应用名称、发布者、导航和图标。

不要默认将旧库全部导入托管存储。现有安装运行链主要支持标准沙箱与隔离 Node 后端；清单类型允许某种声明，不代表目标实例已支持运行。非 Node 后端、保留外部数据库、后台无人值守调用等必须先核实运行支持，再向用户提出具体方案，不能把任意现有网站包进 iframe 就算改造完成。

## 按确认方案实施

先打通身份与一条最小业务链，再替换公共目录和共享组件，接入权限及范围，迁移其余模块，最后补齐安装包与升级路径。只调整接入所需代码，保留用户已有修改与无关业务逻辑。

涉及删除、数据合并、权限放宽、部署或外部系统写入时，先提供具体影响和可核对方案；开发授权不等于生产迁移或部署授权。

## 交付

交付独立项目、锁定版本的工具依赖、测试和构建命令、签名安装包（有发布者密钥时）、权限矩阵、能力接入表、迁移说明和已执行/未执行的验收记录。缺少签名密钥时交付已校验的构建目录并明确缺口，不伪造签名或要求用户把私钥贴进聊天。
