# 隐患提报（识隐）独立应用设计记录

## 旧版功能核对

旧 AFC 项目的 `hazard_records` 是业务台账，`hazard_ai_cases` 是独立的案例检索库。现场原话由模型建议规范描述、分类、等级和治理措施，地点另由车站目录匹配；建议允许人工修改。治理完成后由安全工作岗复审关闭。只有已治理并关闭的记录进入案例库，质量评分达到 70 分才参与检索；训练开关与检索开关分离，自动入库从不启用训练。旧版使用 pgvector 或本地字符向量检索相似案例，并有云文档同步和独立提报入口。

本应用按上述边界实现台账、建议、治理、复审和案例回流。旧版特定组织名称、岗位默认文案、独立登录令牌及云文档同步没有移入平台。案例库是复审闭环经验库，不是未经验证就成为强制标准的法规库。

## 数据与权限

| 对象 | 内容 | 边界 |
| --- | --- | --- |
| 隐患记录 | 提报时间、地点、线路、描述、分类、等级、措施、时限、责任人、治理情况、前后照片引用、状态及版本 | 按应用业务授权过滤；关闭后锁定 |
| 闭环案例 | 关闭时的描述、分类、等级、措施与结果快照、评分、检索和训练标志 | 跟随源记录组织及提报人范围；不存姓名或照片字节 |
| 照片 | 压缩后的 JPEG 和哈希，分块存入应用私有表 | 上传者与记录关联检查；读取再次验证记录范围 |

新建只允许“整改中”；“待复审”必须有治理措施、时限、治理情况和整改后照片；关闭只能由有 `review` 授权且非提报人的员工执行。记录关闭与案例插入为同一原子事务，revision 阻止并发覆盖。案例质量低于 70 分保留但不参与检索。AI 建议在提交前由人确认，不直接写入记录。

照片上传单列 `app.hazards.photo` 授权，提报与治理角色均可获授；服务端还要求目标组织的 `create` 或 `update` 业务授权。照片读取仍使用记录的 `read` 授权。

三个页面各自对应 `app.hazards.create`（隐患提报）、`app.hazards.read`（隐患记录）、`app.hazards.cases`（闭环案例库）。员工应用菜单按角色授权显示；案例接口和 AI 案例检索再次按 `cases` 范围校验。只有提报权限而无案例权限时，AI 不引用案例并提示人工复核。

## 平台能力

新增通用 `platform.ai.complete` Gateway 读操作和 SDK `createPlatformAiClient`。请求仅接受长度受限的 `system` 与 `prompt`，返回长度受限的文本；平台使用管理员配置的 OpenAI 兼容模型并持有密钥。应用必须在签名清单声明 `platform.ai.complete`，管理员审批后才能调用。Gateway 保留应用认证、限流、审计和 30 秒总超时；模型不可用时界面提供手工录入。模型的分类和等级结果由应用枚举校验，相似案例有明确共识时按案例调整并提示人工复核。

照片通过公开文件 SDK 的 `createSandboxImageClient` 和 `createManagedAppImageStore` 上传、存储及读取；后续应用可复用，私有表由 `createAppImageMigrationOperations` 提供。单张上限 220 KB，客户端先缩放压缩；服务端验证块、长度、SHA-256 和 JPEG 首尾标记，关联照片与隐患记录使用同一事务。读取时按源隐患记录业务授权核验。没有在沙箱内直接请求平台文件 URL。

## 当前边界与验收

- 没有迁移旧案例、隐患或账号。初装案例库为空，模型可独立初判并要求人工复核；新闭环会逐步积累案例。
- 案例检索逐页读取全部授权且达到质量门槛的案例，以本地字符二元组相似度排序，内存只保留最相关的 4 条供模型参考；旧案例不会因创建时间被排除。结果大小超限时缩小页大小重试，任何分页失败都使本次建议失败，避免以不完整结果冒充全量检索。这是完整扫描而非向量检索；数据量增长后会增加耗时和 Gateway 调用数，需要平台级索引检索能力。
- “隐患提报”是独立页面，左侧 AI 建议、右侧完整表单；建议只有员工点击“采用建议”后才覆盖对应字段，直接填写不依赖模型。提报时先选线路，再从管理员配置的本工班管辖车站中搜索选择；治理责任人从本工班在岗人员中搜索选择。后端保存时重新核验组织、线路、车站 ID 与责任人 ID，旧版模糊车站匹配尚未移植。
- 照片上传后的未关联块暂无定时回收，需后续平台作业能力支持清理。
- 验收应覆盖手工提报、AI 可用/不可用、组织/本人范围隔离、照片前后上传与读取、证据不全拒绝复审、自审拒绝、并发修改冲突、关闭后原子入库及后续案例建议。
