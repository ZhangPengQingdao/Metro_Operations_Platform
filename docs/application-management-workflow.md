# 应用管理与员工提交审核

## 管理员审核入口

管理员从“应用管理 → 应用审核”处理首次上架和版本更新，待审核申请优先显示。管理员通知铃同时显示这两类申请和员工注册申请。点击应用通知直达对应申请，点击注册通知进入“账号与权限 → 注册审核”。通知根据待审核状态生成，处理后从待办中移除，升级前尚待审核的记录也会显示。通知角标统计全部待办，通知面板分别显示最近 20 条应用申请及最早 20 条注册申请，其余申请可在各自审核列表翻页查看。

## 员工端应用管理

员工端“应用管理”列出本人负责的应用，使用与平台端相同的列表与行操作组件。应用负责人通过行操作打开分栏设置弹窗，维护使用人群、角色及人员分配；应用内不再注入重复的负责人管理菜单。

员工可上传 `mop-app build` 生成的 `.mopkg` 申请上架；应用负责人可提交已有应用的更新包。员工只能查看自己的申请。平台管理员审核时看到与直接安装相同的预览（名称、图标、版本、权限与平台能力、页面、接口、迁移），批准后平台直接安装；驳回可填写原因。

迁移 `app-submissions-expand` 与 `app-submissions-mopkg` 保存安装包、提交人、审核版本、状态和审计记录。相同请求不会创建重复申请，不同包不得复用请求号。同一申请人在相同目标版本下重复提交仍待审、正在安装或结果需核对的包时，返回原申请。单用户最多保留 100 条申请，全部申请包累计上限 512 MiB；达到限制返回错误，不自动删除记录。1.0.0 之前提交的旧版签名包申请如仍待审核，迁移时标记为驳回并提示重新提交 `.mopkg`。

审核进入安装队列后，平台重新核对应用安装版本及提交人的负责人身份，并在安装开始前持久化 processing 状态。执行结果不明时标记 uncertain；两者都禁止重新审核和自动重放，需先在应用列表中核对实际结果。

## 组织人员与单角色模型

应用列表只保留人员管理、角色配置、更新。人员管理使用公开 L2 `OrganizationPeoplePicker`：左侧多级组织树，右侧服务端分页成员，支持搜索与本页全选。组件不持有应用权限，也不自行读取平台接口。

负责人首次保存人员范围时，显式启用新模型并建立普通成员角色。未指定其他角色的范围内人员使用普通成员；普通成员的业务权限需要负责人配置，不会自动获得应用全部权限。普通成员不可停用或改名。

组织选择为动态规则：包含节点及其后代，可排除子组织或个人，排除优先于原有个人包含。负责人可在已排除的工班中重新勾选个人或本页人员；只加入明确选中的人员，不解除整个工班的排除，也不加入其他页或搜索结果以外的人员。再次取消该组织（或其上级）会清除其中重新勾选的人员。

`membership` 的 `audience.personOverrides` 是可选的 `{personId,organizationId}[]`，最多 1000 项，默认空数组；前端仅在重新勾选被组织排除的人员时填写。服务端验证人员当前组织，个人排除、组织停用及离职仍优先；人员调离后原组织的例外不再生效。旧配置未包含此字段时保留原有行为，无需数据迁移。组织调整、人员离职与范围变更在授权时重新核对。角色分配只显示范围内人员，允许逐人切换和最多 500 人的批量替换，每应用每人一条角色分配，数据库主键防止叠加。

迁移 `app-single-role-membership-expand` 是增量迁移，不自动改变既有业务权限。首次切换遇到旧多人多角色或已有工班委派记录会明确拒绝，保留旧规则，不能随机丢弃角色或自动扩权。旧通用委派接口在单角色模式下暂时拒绝，需后续将物料委派改为受约束的单角色切换。

## 平台能力授权

管理端“授权”弹窗只管理负责人和平台能力，不提供业务权限、人员范围或业务角色配置；通过平台 grants 接口新增业务授权会被拒绝。安装或更新时，平台按 `app.json` 的 `platformAccess` 授予平台能力（全部范围），有接口的应用使用服务身份；更新会先清除旧授权再按新版本重新授予。业务角色与数据范围始终由负责人独立配置。

## 状态界面

应用状态使用共享侧边栏弹窗：“运行概况”显示版本、运行状态、后端进程状态、自动重启次数与上次退出；“最近日志”显示应用进程最近的输出。应用已启用但没有运行时可“重新启动”，不会重放任何业务操作。

平台 1.12.0 的数据库初始化会执行 `app-submissions-retry-ids` 增量迁移。重复上传合并到待审核申请时，平台记录已确认的请求号。审核结束后重试同一请求仍返回原申请，重新发起审核使用新请求号。
